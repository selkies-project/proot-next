# proot-next 0.3.9

## Fixes

- A dynamically linked program is loaded where the kernel would put it, below
  its break and far from the libraries and from everything it maps later. It
  was exec'd as the guest's dynamic loader with the program as its argument,
  and the dynamic loader maps such a program wherever `mmap` finds room, among
  the libraries. A JIT that calls into its program with a 32-bit displacement
  whenever the target is less than 4 GiB ahead aborted with "offset is too
  big" once its code cache landed 2 to 4 GiB below the program. A program of
  the host's machine is now exec'd through `l`, a copy of the exec trampoline,
  in the ptrace and no-ptrace tiers: it opens the program and its interpreter
  by guest path, maps them the way the kernel's `binfmt_elf` would and starts
  the interpreter as if the kernel had loaded the program, which goes right
  below the break the kernel set at `ELF_ET_DYN_BASE`. The guest-stub mode
  places programs the same way. `AT_EXECFN` now reads the path the caller
  named, and `/proc/self/maps` starts with the program. 32-bit programs, those
  of another machine, and every program where `l` cannot run keep the dynamic
  loader path. The aarch64 trampoline is now position-independent like the
  x86_64 one, since the kernel moves the break to `ELF_ET_DYN_BASE` only for
  such a trampoline; linked at a fixed address, it left the program above its
  own heap.

## Tests

- A C probe checks that a dynamically linked program lies below its break and
  more than 4 GiB from a new mapping, in every tier.
