# proot-next 0.3.0

## Nested proot and bwrap

A proot or bwrap started inside the guest now works. It cannot be a second
supervisor (the kernel allows one tracer per process and one seccomp
listener per filter chain), so it is not one: an `execve` of proot-next's
own binary, or of any program named `proot`, `proot-next` or `bwrap`, is
served by the supervisor already there. The command line is parsed on the
caller's behalf, every path in it is composed through the caller's view,
and the process that called `proot` becomes the command, in a view of its
own that its children inherit. The caller's child, exit status and signals
are the kernel's own, and nesting composes to any depth.

- proot-apps' graphical installer runs `proot -R app /install` from inside
  its own guest again.
- GTK's glycin image loaders run inside their bwrap sandbox root instead of
  unsandboxed, through the images' `bwrap` symlink or the rootfs's own
  bubblewrap (FileZilla under proot-apps).
- bwrap's `--info-fd`, `--json-status-fd`, `--seccomp`, `--args`,
  `--file`, `--die-with-parent`, `--new-session`, `--clearenv` and
  `--setenv` behave as at top level; `--version`, `--help` and usage errors
  are reported on the caller's own stdout and stderr.
- A nested `-0` or `-k` needs the outer launch to have the same option,
  since the seccomp filter is fixed at start-up, and is refused with a
  message otherwise. `PROOT_NEST=0` turns off the match by name.

The exec trampoline, which carried out every exec without ptrace, now
carries out nested launches in both modes; its record format changed to
carry the environment, the working directory, the caller's seccomp programs
and the status descriptors.

## Hosts with Yama ptrace_scope 2

`kernel.yama.ptrace_scope=2` refuses ptrace and memory access even towards
one's own child unless the caller holds `CAP_SYS_PTRACE` in the child's user
namespace. 0.2.0 stopped there with a misleading "already traced" message
in ptrace mode and left the guest hanging with `PROOT_NO_PTRACE=1`.

- proot-next now tries its accesses on a throwaway child at start-up and,
  when they are refused, runs the guest in a user namespace of its own that
  maps your uid and gid onto themselves. Both modes work that way wherever
  unprivileged user namespaces are allowed. Other users' files read as
  `nobody` through calls the kernel answers directly, and supplementary
  groups as `nogroup`.
- Where that does not help either (Yama 3, or the default Docker and
  Kubernetes `RuntimeDefault` seccomp profiles, which refuse `unshare`
  without `CAP_SYS_ADMIN`), the guests run in the new guest-stub mode on
  x86_64 and aarch64, see below. Elsewhere, or with `PROOT_GUEST_STUB=0`,
  it stops at once with exit status 1 and a message naming the setting and what would
  fix it. In bwrap mode the message carries bubblewrap's "No permissions to
  create a new namespace" wording.
- `PROOT_USERNS=1` forces the user namespace, `PROOT_USERNS=0` rules it out.

## Guest-stub mode

For hosts where neither ptrace nor a user namespace reaches the guest's
memory, such as a container under Docker's default profile at Yama scope
2. The filter traps the served syscalls into a handler inside
each guest, which copies the paths and buffers they use into memory shared
with the supervisor and copies the results back. Every exec goes through
the trampoline, which now loads the program and its interpreter in place,
as the kernel would, so the handler stays armed; `AT_EXECFN` names the
program in the auxiliary vector the kernel keeps as well as in the one the
program starts with, so uutils' coreutils, which pick their applet by it,
run. Taken where nothing else
works, or anywhere with `PROOT_GUEST_STUB=force`. x86_64 and aarch64
hosts, for their 64-bit and 32-bit programs: a 32-bit build of the
trampoline, `e32`, carries the handler into i386 or 32-bit ARM processes.
Firefox and Chromium render, the GTK4 proot-apps installer runs with its
glycin loaders, i386 and armhf Debian rootfses run apt and gcc, and the
e2e suite passes in it on both hosts. Steam in a locked-down selkies
container falls back to it for pressure-vessel and runs games through every
runtime path it uses: native, native 32-bit, Proton, and Proton with 32-bit
Windows programs.

The x86_64 trampoline is now a static position-independent executable; the
others are linked at `0xd0000000`.

## Fixes

- A run without ptrace no longer hangs after its guest exits on Linux 6.8
  (Ubuntu 24.04's kernel), which leaves a thread waiting for a notification
  asleep when the last guest process leaves; the supervisor watches the
  listener's hangup itself.
- The exec trampoline builds the argument and environment vectors it hands
  to `execve` in zeroed storage written through its own address, rather
  than in arrays seeded with null pointers.
