# proot-next 0.2.0

## Runs where ptrace is filtered out

A container profile that denies the `ptrace` syscall (a hardened Docker or
Kubernetes seccomp profile) used to stop proot-next at start-up. It now
notices and runs without the ptrace tier, since the listener, `process_vm_readv`
and `/proc/<pid>/mem` are still allowed there. ptrace remains the first
choice where it works.

- `chdir`, `fchdir` and `chroot` are answered with a virtual working
  directory per process; the kernel's cwd of every tracee is pinned to the
  supervisor's alias directory.
- Unix-socket `connect` and `bind` are done by the supervisor on a socket of
  the same type and flags, swapped into the tracee's descriptor.
- `execve` goes through a static trampoline installed under
  `$XDG_RUNTIME_DIR`: the path string is rewritten in place to its two-byte
  name and a record file carries the real target and arguments. Scripts,
  `#!`-less files (`ENOEXEC` for the shell), `posix_spawn`, `fexecve` and
  32-bit programs all work; `/proc/self/exe` and `comm` still name the
  program.
- `inotify_add_watch` and the `O_PATH` opens that cannot be served with a
  read-only descriptor use a transient alias, restored to the caller's buffer
  only when that memory is verifiably untouched.
- Processes are discovered at their first syscall and inherit their parent's
  state, with snapshots taken at `clone` so a daemon's double fork keeps its
  working directory; exits come from pidfds. The supervisor is a child
  subreaper, so a daemon reparented away from its parent stays its
  descendant, which Yama's default `ptrace_scope` requires for memory access.

`PROOT_NO_PTRACE=1` forces the mode for testing. The e2e suite runs in both
modes; the known gaps are listed in `docs/ARCHITECTURE.md`.

## Namespaces inside the guest are refused

`clone`, `clone3` and `unshare` with a `CLONE_NEW*` flag, and `setns`, get
`EPERM`, as they do in a default container. On a host that allows
unprivileged user namespaces, bubblewrap started by GTK's glycin image
loaders (FileZilla, any GTK 4 application) used to build a real mount
namespace that the supervisor could not serve, and the application aborted
on its first icon. It now gets the refusal it already handles and runs its
loaders unsandboxed, as it does in Docker.

A nested proot-next in bwrap mode, which a program inside a guest can start
by finding the images' `bwrap` symlink on its `PATH`, now fails with
bubblewrap's own "No permissions to create a new namespace" instead of a
proot error, so the same fallback applies.

## Fixes

- The listener pool no longer quits when a queued notification is withdrawn
  by a signal (a SIGCHLD landing on a shell mid-`stat`), which left every
  later syscall of the tracees unanswered. Shutdown is now confirmed by the
  listener's `POLLHUP`.
- A relative `-r`/`-R` path is made absolute at start-up, so loader aliases
  and the exec shim resolve it from anywhere.
- A program started through a symlink finds the libraries its `$ORIGIN`
  rpath names: the dynamic loader is handed the resolved program path, the
  one the kernel would have used, while `argv[0]` keeps the name as typed.
  WebCord and other Electron applications failed to load their bundled
  `libffmpeg.so` from `/usr/bin/<app>` links.
- `/proc/<pid>/cmdline` reads as the argv the process was started with, so
  `ps`, `pgrep -f` and programs inspecting their own command line no longer
  see the dynamic loader the exec was retargeted at.
- A process is named as the kernel would name it: `comm` takes the last
  component of the path given to `execve`, so a `#!` script shows under its
  own name rather than its interpreter's.
